# 花再 Halo PixelBar 控制协议记录

本文档记录了本机实测 + 公开实现交叉验证得出的设备控制协议，供后续维护参考。

---

## 一、设备与接口定位

### 设备标识

| 项目 | 值 |
|---|---|
| 产品名 | 花再 Halo PixelBar |
| 制造商 | Jieli Technology（杰理科技） |
| 序列号 | `415035313539340C` |
| VID / PID | `0x2D99` / `0xA106` |
| 复合设备 | `USB\VID_2D99&PID_A106` |

### 三个 HID 接口（实测，报告描述符解析）

| 接口 | Usage Page | 报告 ID（输出/输入） | 数据区 | 用途 |
|---|---|---|---|---|
| `MI_03` | `0x000C` | — / 0（1 字节） | 1 字节 | 消费者控制（媒体按键） |
| `MI_04` Col01 | `0xFF13` | 6 / 7 | 61 字节 | 厂商自定义（非像素屏通道） |
| **`MI_04` Col02** | **`0xFF14`** | **46 / 47** | **63 字节** | **像素屏通道 ← 用这个** |

### 为什么确定是 Col02

`HaloPixelToolBox`（C#）的设备筛选条件是：

```csharp
device.GetMaxInputReportLength() == 64 && name.Contains("花再 Halo PixelBar")
```

Windows 下 `HIDP_CAPS.InputReportByteLength` **包含报告 ID 字节**：

- Col02：输入报告 63 + 1（报告 ID）= **64** ✅ 命中
- Col01：输入报告 61 + 1 = 62 ❌

同时 Col02 的输出报告 ID 是 **46 = 0x2E**，正好等于所有命令包的首字节。

> **这解释了那个"魔数"**：Python 移植版把 `0x2E AA EC E8` 记成了魔数，
> 其实 `0x2E` 是 HID 报告 ID，真正的魔数是 `AA EC E8`。
> 63 字节数据区 + 1 字节报告 ID = 64。

### 权限

本机实测：**普通用户权限即可打开**这三个接口并成功写入，不需要管理员。
（`HaloLyricSync` 的 README 写着需要管理员，本机不成立。）

## 二、数据包格式

所有包固定 **64 字节**，通过 HID **输出报告**（不是 Feature Report）发送。
`hidapi` 里用 `dev.write(packet)`，`packet[0]` 就是报告 ID。

### 1. 文本包

```
偏移  长度  内容
0x00  4     2E AA EC E8        （2E = 报告 ID）
0x04  1     00                 保留
0x05  2     总长度（小端）       = 1 + 文本字节数 + 1
0x07  1     文本字节数（UTF-8）
0x08  N     文本内容 UTF-8
0x08+N 1    校验和
...   补 00 至 64 字节
```

- **文本包不带颜色**，颜色由布局包设置
- 校验和算法：
  ```python
  acc = 128
  for b in text_bytes:
      acc += b + 2
  checksum = acc % 256
  ```
- **单包上限**：`64 - 5 - 2 - 1 - 1 = 55` 字节 UTF-8
  → 汉字每个 3 字节，最多 18 个；ASCII 最多 55 个

### 2. 布局包

```
0x00  6     2E AA EC EF 00 09
0x06  9     payload
0x0F  1     校验和
0x10  1     00
...   补 00 至 64 字节

payload = 01 | R G B | 00 02 | sub | mode | FF
```

| 字段 | 值 |
|---|---|
| `sub` | `0x00` 对齐类 / `0x01` 滚动类 |
| `mode` | 对齐：`00` 左 `01` 居中 `02` 右 `03` 拉伸<br>滚动：`00` 左→右 `01` 右→左 |

六种布局的完整包首 16 字节（白色 `FF FF FF`）实测：

| 布局 | sub | mode | 首 16 字节 |
|---|---|---|---|
| `left` | 00 | 00 | `2e aa ec ef 00 09 01 ff ff ff 00 02 00 00 ff 8d` |
| `center` | 00 | 01 | `2e aa ec ef 00 09 01 ff ff ff 00 02 00 01 ff 8e` |
| `right` | 00 | 02 | `2e aa ec ef 00 09 01 ff ff ff 00 02 00 02 ff 8f` |
| `stretch` | 00 | 03 | `2e aa ec ef 00 09 01 ff ff ff 00 02 00 03 ff 90` |
| `scroll_left_to_right` | 01 | 00 | `2e aa ec ef 00 09 01 ff ff ff 00 02 01 00 ff 8e` |
| `scroll_right_to_left` | 01 | 01 | `2e aa ec ef 00 09 01 ff ff ff 00 02 01 01 ff 8f` |

### 长句为什么要用设备滚动

屏幕一行物理上放不下整句歌词（约 20 列），早期做法是把句子切页来回翻 ——
观感是"一闪一闪"，而且和下一句歌词的界限模糊，容易误读。

设备**自带硬件滚动布局**（`sub=0x01`），所以正确做法是：
整句原样发过去，让设备自己平滑滚动。程序只需在"长句 / 短句"之间切换布局，
并且只在布局真的变化时才发一个布局包（不额外增加 HID 写入）。

`bridge/halo_bridge.py` 的 `Renderer.emit()` 实现这个策略：

- `display.scroll_always`（默认 `true`）—— **所有文本都用滚动布局**，不分长短。
  实测短句也会一起滚，所以整体观感统一，不会出现"有的句子静止有的在动"。
  设为 `false` 时才按长短区分：短句用 `layout` 对齐静态显示，长句按 `long_line_mode` 处理。
- `display.long_line_mode` —— `scroll`（默认）/ `paging`（旧翻页）/ `cut`（截断）
- `display.scroll_direction` —— 默认 `right_to_left`（由右往左）

`ensure_layout()` 只在布局真的变化时才发布局包；`scroll_always=true` 时布局全程不变，
所以整首歌下来只会发**一个**布局包（启动时由 `set_style()` 发出），零额外开销。

> 本机实测（花再 Halo PixelBar）：滚动是**平滑飘过**，而且**播完自动循环**，
> 所以 `display.scroll_repeat_seconds` 保持 `0` 即可，不需要定时重发。
> 换其它固件/型号时若发现"飘一次就停住"，再把它设成 `4.0`。

### 屏幕列宽怎么量

`max_columns` 决定"多长的句子才需要滚动"。设小了会让本来放得下的句子也滚动，
设大了会被屏幕裁掉。用 `--ruler` 实测：

```bash
python bridge/halo_bridge.py --ruler     # 或双击 measure-screen.bat
```

原理：用**左对齐**布局（不滚动）发一串 18 个不同汉字（54 字节，卡在单包上限内），
每个汉字占 2 列，用户看到第几个字被裁掉就知道屏幕实际列宽。
连续发多把尺子会互相覆盖，所以量之前要先停掉正在跑的同步。

**单包文本上限与退化策略**：文本包最多装 55 字节 UTF-8（约 18 个汉字）。
```python
MAX_TEXT_BYTES = 64 - 5(头) - 2(总长) - 1(文本长) - 1(校验和)   # = 55
```
所以当长句超过 55 字节时，**连滚动也滚不全**。这种情况程序会自动退回分页
（每页不超过 `max_columns`，即 ≤27 列 = 54 字节，一定装得下），
避免 `build_text()` 静默截断导致内容丢失。

校验和（注意初值是 124，且只对 payload）：

```python
acc = 124
for b in payload:
    acc += b + 2
checksum = acc % 256
```

> **颜色就是在这里下发的**，RGB 三字节直接写在 payload 里。
> Python 移植版把它简化成了"文本包第 5 字节填 0～6 的调色板索引"，
> 本实现采用官方 C# 做法（布局包带 RGB），更可靠。

### 4. 其他命令（未在本程序中启用）

同一个 `2E AA EC ??` 家族里还有：

## 五、EchoMusic 侧

### 版本要求

本机实测 **2.3.2-beta.13**，插件所需能力：

| 能力 | API | 起始版本 |
|---|---|---|
| 读歌词与进度 | `ctx.nowPlaying.getSnapshot()` / `onSnapshot()` | 2.2.6-beta.20 |
| 本机 HTTP 服务 | `ctx.webServer.listen()` | 已有（早于 WebSocket） |
| 本机 WebSocket（可选） | `ctx.webServer.onConnection()` | 2.3.2-beta.6 |

> 本程序的桥接端**只用 HTTP 轮询**，不依赖 WebSocket —— 因为拿到
> `currentTime + updatedAt + playbackRate` 后可以在本地精确推算播放位置，
> 轮询延迟不影响歌词行的准确性，反而少一个依赖。
> 插件仍然会在同一端口上接受 WebSocket 连接，需要时可以改用推送。

manifest 里的版本门槛写成 `>=2.2.6-beta.20`（即 Now Playing 快照的起始版本），
而不是 WebSocket 的版本 —— 避免不同 semver 实现对 `beta.13` / `beta.6`
这种预发布号比较不一致导致插件被误判为"版本不符"。


### 拿到的数据

```js
snapshot.playback.{ title, artist, album, duration, currentTime,
                    updatedAt, playbackRate, isPlaying }
snapshot.lyric.{ lines[], currentIndex, timeOffset, loading }
snapshot.appearance.accentColor
```

### ⚠️ 时间单位（踩过坑，务必注意）

实测真实快照（2026-10-14，歌曲《老人と海》，时长 255.47 秒）：

```jsonc
"currentTime": 81.2896,          // ← 秒
"duration": 255.4685,            // ← 秒
"updatedAt": 1791976576685,      // ← 毫秒（Unix 时间戳）
"currentIndex": 17,
"lines": [
  { "t": "ヨルシカ - 老人と海 (老人与海)", "s": 0,      "e": 0, "r": "" },
  { "t": "作词：n-buna",                "s": 3.278,  "e": 0, "r": "" },
  ...
  { "t": "海のずっと向こうにある",        "s": 249.562,"e": 0, "r": "" }
]
```

**`s`（歌词行起始时间）的单位是「秒」，不是毫秒。**
只有 `updatedAt` 是毫秒。混用会直接毁掉歌词定位：

| 处理方式 | 结果 |
|---|---|
| 把 `s` 当毫秒（错误）| 二分查找永远溢出 → 卡在最后一行 |
| 把 `s` 当秒（正确）| 命中下标 17 = `海の方へ`，与插件 `currentIndex` 一致 |

`bridge/halo_bridge.py` 的 `line_starts_ms()` 做了单位自动识别：
歌词时间轴应大致落在 `[0, duration]`，按秒算 `max(s)/duration ≈ 1`，
按毫秒算 `≈ 1000`，所以用「是否超过 `duration` 的 10 倍」来区分。
配置项 `source.time_unit` 可强制指定（`auto` / `seconds` / `milliseconds`）。

另外 `current_line_index()` 会用插件的 `currentIndex` 做交叉校验：
两者偏差超过 5 行时以 `currentIndex` 为准，避免时间轴不可靠时显示错乱。

> 顺便一提：这类歌曲的第 0 行歌词往往就是「歌手 - 歌名」，
> 所以歌曲开头屏幕上出现歌名是正常的，不是 bug。

### 关键的时序问题

`playback.currentTime` 是**离散采样值**，不是逐帧时钟。官方文档明确要求：

> 对时序敏感的插件，应使用 `playback.currentTime`、`playback.updatedAt` 和
> `playback.playbackRate` 在本地推算当前播放时间。

本程序的用法（`bridge/halo_bridge.py` 的 `estimated_position_ms()`）：

```
位置 = currentTime×1000 + (now − updatedAt) × playbackRate + lyricOffset
```

再对歌词行的 `startTime` 做二分查找得到当前行。
如果某首歌没有逐行时间戳，退回使用插件给的 `currentIndex`。

### 为什么必须有插件

EchoMusic 没有对外暴露类似 LX Music 的开放 API 端口（LX Music 是 23330），
外部进程读不到播放状态，所以插件是唯一的数据出口。

## 六、维护提示

- 设备固件升级后协议可能变。若失效，先用 `python bridge/halo_hid.py` 复核接口与报告 ID
- `bridge/halo_hid.py` 里的 `enumerate_candidates()` 会自动按报告 ID 打分排序，
  所以换一台同型号设备（甚至换 USB 口）都不需要改配置
- 若写入失败，`_write()` 会自动回退尝试 `send_feature_report`
